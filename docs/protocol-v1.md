# go-dock 设备通信协议 v1

本文档描述 go-dock 主机程序（`host/`）与微雪 ESP32-S3-Touch-AMOLED-2.41-B 固件（`firmware/`）之间的协议。屏幕显示的一切（任务、额度、读数条、提示音、亮度）只走 WiFi，即局域网 TCP（§1.1）；USB 串口只用来设置屏幕的 WiFi 和升级固件（§1.2）。固件也能经 WiFi 升级，但要在屏幕上点确认（§3.4）。两端实现必须与本文档保持一致；改动协议时，需同时修改本文档和 `host/internal/device/protocol.go`。

## 1. 连接

USB 串口的物理约定：

| 项目 | 约定 |
|---|---|
| 接口 | 板载 USB-C，直连 ESP32-S3 原生 USB（GPIO19/20），无 USB-UART 桥接芯片 |
| USB ID | 默认 USB-Serial/JTAG：`303A:1001`；若固件改用 TinyUSB CDC，ESP-IDF 默认 `303A:4001`。主机会把所有 VID 为 `303A` 的串口视为候选，并优先选择 PID `1001`/`4001` |
| 端口名 | macOS `/dev/cu.usbmodem*`（主机只打开 `cu.*`，不打开 `tty.*`）；Linux `/dev/ttyACM*`；Windows `COMx` |
| 波特率 | 原生 USB 无意义，主机固定传 115200 |
| 控制线 | 主机打开端口时 **DTR=1、RTS=0**。在 USB-Serial/JTAG 上翻转 RTS 可能触发芯片复位；TinyUSB CDC 通常把 DTR 当作「主机已连接」 |
| 编码 | UTF-8 |

**固件日志**：ESP-IDF/Arduino 的控制台日志和 ROM 启动信息默认也走这个端口。建议把控制台改到 UART0 或关闭（`CONFIG_ESP_CONSOLE_NONE` / 关闭 USB CDC On Boot 的日志），需要上报的日志改用下文的 `log` 消息。主机会忽略所有不是协议消息的行（只记 debug 日志），所以残留的启动输出不会破坏通信，但会浪费带宽。

### 1.1 WiFi（数据）

屏幕用 `wifi`（§3.7，只能经 USB 发送）连上 WiFi 后，在 **TCP 47322** 端口监听。主机连上后发 `hello`、`snapshot`、`line`、`settings`、`beep`，需要时还有固件升级（§3.4），设备回 `hello`、`ack`、`log`、`ota`、`denied`；帧格式见 §2。

| 项目 | 约定 |
|---|---|
| 地址 | 主机手动配置屏幕的 IP（不做 mDNS）。屏幕在「连接信息」页和「等待 go-dock」「主机离线」卡片上显示自己的地址和配对码（§7.1） |
| 配对 | 屏幕第一次启动支持 WiFi 的固件时生成 6 位数字配对码，存起来不再变。主机的第一条消息必须是带正确 `code` 的 `hello`（§3.1），之前的消息一律忽略；`code` 不对时设备回 `denied`（§4.7）并断开，2 秒内来的新连接也直接回 `denied` 断开，拖慢猜码 |
| 多台电脑 | 设备最多同时连 4 个 go-dock（每个一条 TCP 连接），每台电脑一页，轮流显示（§7.1「多台电脑」）。每台的 `snapshot`、`line` 各自保存；`settings` 以最后收到的为准（§3.3）；`beep` 哪台发来都响；固件升级同一时间只有一条连接（§3.4）。设备发出的 `log` 给所有连着的 go-dock。同一个 go-dock（`hello` 的 `id` 相同）换了一条连接时，新连接接替，旧连接收到 `denied` |
| 只在 USB 上的 | 改 WiFi（§3.7、§3.8，§1.2）。固件升级两条连接都行，经 WiFi 时要在屏幕上确认（§3.4） |
| 超时 | 连上后 5 秒内没有正确的 `hello`，设备断开；连接 20 秒没有任何消息，两端都断开（主机每 5 秒心跳，设备每个 `snapshot` 都回 `ack`） |
| 安全 | **明文**：任务标题、消息、正在执行的命令都会以明文在局域网里传输。配对码只防止局域网里的其他人往屏幕上推送数据 |

### 1.2 USB（设置和升级）

屏幕插着 USB 线时，go-dock 打开串口，只用它做两件事：设置 WiFi，升级固件。USB 上的消息只有：

| 方向 | 消息 |
|---|---|
| 主机 → 设备 | `hello`（不带 `code`）、`wifi`（§3.7）、`wifi_scan`（§3.8）、固件升级（§3.4） |
| 设备 → 主机 | `hello`、`net`（§4.5）、`wifi_list`（§4.6）、`ota`（§4.4）、`log` |

设备忽略 USB 上的 `snapshot`、`line` 等数据消息，屏幕的内容不受 USB 影响。设备上电时先在 USB 上发一次 `hello`。主机收到不是回复自己的 `hello` 时（设备重启了），回一个自己的 `hello`：刚升级的固件要听到 go-dock 才会留下（§3.4），否则 2 分钟后回到旧固件。设备的 WiFi 状态一变就在 USB 上发 `net`，不等主机问。USB 也不需要配对码：能插线的人本来就能刷屏幕。

## 2. 帧格式

- 每条消息是**一行 JSON 对象**，以 `\n` 结尾（设备发送 `\r\n` 也可以）。
- 一行（含结尾换行）**不超过 4096 字节**。超长的行，接收方整行丢弃。主机保证不超：`snapshot` 先从最不紧急的会话开始删 `agents[]` 条目（`agents_total` 和 `agents_active` 保留），还超再从末尾删会话；`line` 的读数最多 8 项、每项字数有上限（§3.5），总能放下。
- 每个对象都有字符串字段 `t` 表示消息类型。
- 字符串不做 HTML 转义（`<`、`>`、`&` 原样发送）；非 ASCII 字符直接以 UTF-8 发送，不转成 `\uXXXX`。
- 时间一律为 **Unix 秒**（整数）。值为 `0` 表示「未知」。
- 接收方必须**忽略不认识的字段**和不认识的 `t`，以便向后兼容。

## 3. 主机 → 设备

### 3.1 `hello`

主机连上屏幕（TCP，或打开 USB 串口）后立即发送；在收到设备 `hello` 之前，每 5 秒重发一次。

```json
{"t":"hello","proto":1,"name":"Mac mini","id":"3f9a2c1d","code":"482916"}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `proto` | int | 协议主版本，本文档为 `1` |
| `name` | string | **可选**。本机名称，最多 20 个字，是屏幕上这台电脑那一页的标题（§7.1）。默认是电脑的名称（macOS 系统设置里的「电脑名称」，如「User 的 Mac mini」；其他系统为主机名） |
| `id` | string | **可选**。同一个 go-dock 不变的标识，`[a-z0-9]{1,16}`；同一个 go-dock 换了连接（比如从 USB 改成 WiFi）时，设备据此让新连接立刻接替 |
| `code` | string | **网络连接必填**（§1.1）。屏幕的 6 位配对码；USB 上不发 |

设备收到后应回复自己的 `hello`（见 4.1）。

### 3.2 `snapshot`

完整的显示状态。设备收到后**整体替换**当前状态，不需要做增量合并。

发送时机：
- 连上屏幕后立即发送一次（不等设备握手）
- 收到设备 `hello` 后立即发送一次
- 状态变化时发送（200 ms 防抖）
- 心跳：每 5 秒发送一次，即使没有变化

```json
{
  "t": "snapshot",
  "seq": 128,
  "now": 1792202470,
  "tz": 28800,
  "usage": {
    "claude": {
      "five_hour": {"pct": 62.0, "resets_at": 1792209670, "window_min": 300},
      "seven_day": {"pct": 31.0, "resets_at": 1792600000, "window_min": 10080},
      "today_tokens": 1834567,
      "today_cost": 12.84,
      "updated_at": 1792202400
    },
    "codex": {
      "five_hour": {"pct": 28.0, "resets_at": 1792210000, "window_min": 300},
      "seven_day": null,
      "today_tokens": 402113,
      "updated_at": 1792202300
    }
  },
  "sessions": [
    {"id": "claude:0f4f5b10-…", "p": "claude", "project": "go-dock", "state": "approval", "since": 1792202428, "title": "清理 ssh 配置",
     "agents": [
       {"type": "Explore", "text": "查看 ssh 配置与密钥代码", "state": "approval", "since": 1792202428},
       {"type": "Explore", "text": "查看工具栏与存储", "state": "running", "since": 1792202410}
     ],
     "agents_total": 3, "agents_active": 2},
    {"id": "codex:0199a1…", "p": "codex", "project": "api-svc", "state": "running", "since": 1792202278, "title": "重构登录模块", "detail": "Bash: pytest -q tests/auth"},
    {"id": "claude:4a51cb15-…", "p": "claude", "project": "blog", "state": "done", "since": 1792202350, "msg": "Release notes are ready."}
  ],
  "counts": {"approval": 1, "input": 0, "running": 1, "done": 1, "error": 0, "idle": 2},
  "total": 3
}
```

**顶层字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `seq` | uint | 递增序号，每发一次 `snapshot` 加 1；主机重启或重连后可能从小的值重新开始 |
| `now` | int | 主机当前时间。设备不需要 RTC，倒计时和经过时长都基于它计算（见 7.2） |
| `tz` | int | 主机所在时区相对 UTC 的偏移（秒，东八区为 `28800`），设备显示本地时钟用 |
| `usage` | object | 固定包含 `claude` 和 `codex` 两个键，结构见下表 |
| `sessions` | array | 任务列表，**已按显示顺序排好**，设备不要重新排序 |
| `counts` | object | 各状态的会话数，包含被过滤掉的 `idle` |
| `total` | int | 应显示的任务总数（已排除 `idle`）。`sessions` 可能因数量上限或 4 KB 限制比它短，设备可显示「+N」 |

**`usage.claude` / `usage.codex`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `five_hour` | object \| null | 5 小时额度窗口；未知时为 `null` |
| `seven_day` | object \| null | 7 天额度窗口；未知时为 `null` |
| `five_hour.pct` / `seven_day.pct` | number | 已用百分比 0–100，可能有小数 |
| `*.resets_at` | int | 重置时间；`0` 表示未知。重置时间已过时，主机会发 `pct: 0, resets_at: 0` |
| `*.window_min` | int | 窗口长度（分钟），通常为 300 / 10080；`0` 表示未知。标签可据此显示「5h」「7d」 |
| `today_tokens` | int | 今日（主机本地时区）token 数 = 输入 + 缓存写入 + 输出，**不含缓存读取**（每轮重复读取同一段上下文，会占到总数的 99%） |
| `today_cost` | number | 今日按 API 价格估算的费用（美元）。**仅 Claude 有**，无法估算时省略该字段 |
| `updated_at` | int | 额度数据的更新时间；`0` 表示从未获取。可据此提示数据陈旧 |

**`sessions[]`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 稳定的会话 ID（`provider:session_id`），可用于翻页后保持选中项 |
| `p` | string | `claude` 或 `codex` |
| `project` | string | 工作目录名，最多 24 个字符（按 Unicode 字符计） |
| `state` | string | `approval` / `input` / `error` / `running` / `done` / `idle` |
| `since` | int | 进入当前状态的时间 |
| `title` | string | **可选**。会话名：用 `/rename` 改过时为改的名字，否则为自动生成的标题（Claude Code、Codex 都会在第一次提问后生成）；Codex 还没有标题时为第一次提问。最多 32 个字符。和 `detail` 相同或没有时省略 |
| `msg` | string | **可选**。AI 本轮最新一段回复的第一行（和 Claude Code 界面里 ● 开头的那句一样），去掉 Markdown 标记，按一行屏幕宽度截断（见下）。新一轮提问时清空；没有时省略。行太长时最先被去掉（在子代理之后、会话之前） |
| `detail` | string | **可选**。会话**自己**当前的动作，按一行屏幕宽度截断（见下）。运行中的命令显示 Claude 为它写的说明（如 `Check hooks install`，和 Claude Code 界面里命令上方那行一样），没有说明时显示 `工具: 参数`；Codex 的命令没有说明，显示 `Bash: 命令`，改文件显示 `apply_patch: 文件名`；等授权时总是显示实际命令（如 `Bash: rm -rf dist`）。Codex 调用 `request_user_input` 提问时状态为 `input`，`detail` 为「等待回答问题」（和 Claude Code 的 AskUserQuestion 一样）。会话自己这一轮已结束、但还有子代理在跑时，为「等待 N 个子任务完成」 |
| `turn_output` | int | **可选**。本轮（从用户这次提问开始）AI 输出的 token 数，和 Claude Code 转圈提示里的 `↓ 6.5k tokens` 一样；新一轮从 0 开始，为 `0` 时省略 |
| `turn_secs` | int | **可选**。截至 `now`，本轮 AI 已工作的秒数，和 Claude Code 转圈提示里的时间一样：**不含等用户授权、回答的时间**。会话（含子代理）从空闲变忙或用户提问时开始一轮，变回空闲时结束；后台子代理还在跑时继续计时。为 `0` 时省略 |
| `agents` | array | **可选**。会话的子代理（Claude Code 的 Agent 工具、Codex 派生的子线程），最紧急的在前，最多 3 个。没有子代理时省略 |
| `agents_total` | int | **可选**。子代理总数（含未列出和刚完成的）。没有子代理时省略，按 `0` 处理 |
| `agents_active` | int | **可选**。其中仍在工作或等待用户的个数。为 `0` 时省略 |

`msg` 和 `detail` 各占满一整行，按显示宽度截断：中文、日文、韩文、全角符号和 emoji 算 2 列，其他字符算 1 列，最多 64 列（约 30 个汉字或 60 多个英文字符），同时不超过 148 字节（固件缓冲区 152 字节，避免截断半个字符）；截断时以「…」结尾。

`state`、`label`、`text`、`since` 描述的是**会话本身和它的子代理中最紧急的那个**：子代理在等授权时，整行就是 `approval`，`text` 写成「`<子代理类型> · <它在做的事>`」，`since` 是该子代理的开始时间。会话本身这一轮已结束（`done` / `idle`，比如 Claude Code 派出后台子代理后就停下等结果）、但子代理还在跑时，整行是 `running`，`detail` 是「等待 N 个子任务完成」。

**`agents[]`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `type` | string | 子代理类型，如 `Explore`、`general-purpose`、Codex 的角色名（没有角色时为它的昵称，如 `Kepler`）；最多 16 个字符 |
| `text` | string | 它被派去做的事（任务描述），没有时为它当前的动作；它在等授权、等输入或出错时，改为它要做的动作（如 `Bash: rm -rf dist`）。最多 32 个字符，可能为空 |
| `state` | string | `running` / `approval` / `input` / `error` / `done`（刚完成的会保留约 3 分钟） |
| `since` | int | 开始时间 |

**`state` 取值与显示顺序**（主机已按此排序；同一状态内最近更新的在前）

| state | label | 含义 | 建议颜色 |
|---|---|---|---|
| `approval` | 需授权 | 等待用户批准工具调用 | 琥珀色 `#FFB020` |
| `input` | 等待输入 | 等待用户回答问题、处理对话框 | 蓝色 `#3B9EFF` |
| `error` | 出错 | 本轮因错误结束（如限流） | 红色 `#FF5A5F` |
| `running` | 进行中 | 正在执行 | 绿色 `#3DDC84` |
| `done` | 已完成 | 本轮刚结束（默认保留 30 分钟） | 灰色 `#8A8F98` |
| `idle` | 空闲 | 会话开着但无事可做；默认不发送 | 深灰 |

### 3.3 `settings`

屏幕亮度。设置保存在 go-dock 里（网页「设置」），每次修改时发；握手后只在用户改过默认值（80、20、5 分钟），或者屏幕离线期间改过时才发：几台电脑共用一块屏幕时，没动过设置的那台不会盖掉别人设的亮度。设备以最后收到的为准。

```json
{"t":"settings","brightness":80,"dim_brightness":20,"dim_after":300}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `brightness` | int | 亮度，百分比 10–100 |
| `dim_brightness` | int | 变暗后的亮度，百分比 0–100，`0` 为熄屏；高于 `brightness` 时按 `brightness` |
| `dim_after` | int | 没有活跃任务（需授权、等待输入、出错、进行中）多少秒后变暗，最多 86400；`0` 为不变暗 |

超出范围的值取最近的有效值，缺少的字段保持原值。设备把设置存起来（NVS），重启后、go-dock 连上之前也照此执行。什么时候亮、什么时候暗由设备自己判断，因为触摸、断线这些只有它知道：

- 任何一台电脑有任务需要你处理（需授权、等待输入、出错）、升级固件时，保持 `brightness`；
- 触摸后 1 分钟内保持 `brightness`，屏幕暗着时第一下点击只用来点亮；
- 所有电脑的最后一个活跃任务结束 `dim_after` 秒后，降到 `dim_brightness`；
- 和主机断开 15 秒后降到约 16%，10 分钟后降到约 5%，都不高于 `brightness`。

### 3.4 固件升级

主机把固件程序镜像（Release 里的 `go-dock-firmware-v2-app.bin`，不是从 `0x0` 开始刷的合并镜像）分块发给设备，设备写入空闲的 OTA 分区后重启进入新固件。屏幕插着 USB 线时走 USB，否则走 WiFi。

**经 WiFi 时要在屏幕上确认**：设备收到 `ota_begin` 先不擦除，回 `confirm`（§4.4），屏幕弹出确认卡片（§7.1「确认升级」），写明新旧版本和发起的电脑（`hello` 的 `name`）。用户点「升级」后设备回 `confirmed`，然后擦除、回 `ready`，之后和 USB 一样；点「取消」或 60 秒没人点，设备回 `error`（「已在屏幕上取消」「屏幕上没有人确认，已取消」）。等待确认和擦除期间这条连接算作有消息，不会因为静默被断开，别的 go-dock 也抢不走屏幕。主机等确认最多 75 秒，等到 `confirmed` 后再按 `ready` 的 60 秒等擦除。经 USB 升级不用确认：能插线的人本来就能刷屏幕。

同一时间只有一条连接能升级：一条连接在升级（或在等确认）时，另一条发来的 `ota_begin` 得到 `error`「屏幕正在经另一条连接升级固件」，它发来的其他升级消息也不起作用。正在升级的那条 WiFi 连接断开时，设备放弃本次升级。

```json
{"t":"ota_begin","size":4013664,"ver":"0.1.4"}
{"t":"ota_data","off":0,"data":"6QYCT7RWN0Ds…"}
{"t":"ota_end"}
{"t":"ota_abort"}
```

| 消息 | 字段 | 说明 |
|---|---|---|
| `ota_begin` | `size`、`ver` | 开始一次升级：镜像字节数和镜像里的版本号。设备擦除目标分区（约 10 秒）后回复 `ready` |
| `ota_data` | `off`、`data` | 镜像从 `off` 开始的一段，`data` 为标准 base64，解码后最多 2048 字节。`off` 必须等于设备已写入的字节数 |
| `ota_end` | — | 镜像发完。设备校验镜像摘要、项目名（`go-dock-firmware`）和版本号，设为启动分区，回复 `done` 后约 1 秒重启 |
| `ota_abort` | — | 放弃本次升级，设备继续运行原固件 |

每条消息都要等设备回复（见 §4.4）后才发下一条，不能连发：设备 USB 接收缓冲有限（16 KB），满了会静默丢数据。主机的等待时间：`ready` 60 秒（经 WiFi 时先等 `confirmed` 75 秒），`ack` 10 秒，`done` 30 秒；超时或收到 `error` 时发送 `ota_abort` 并报告失败。升级期间主机不经这条连接发 `snapshot`；经 WiFi 升级没成功时，主机接着发 `snapshot`。

设备 15 秒没收到下一块数据就自动放弃。新固件启动后处于试用状态：收到主机的 `hello` 或 `snapshot` 才确认保留（USB 或 WiFi 都算）；确认前重启，或 2 分钟内没联系上主机，bootloader 会回到原来的固件。主机在设备回复 `done` 后等待新版本的 `hello`：版本对上即成功；5 秒后仍报告旧版本，或 60 秒内没有报告，按失败处理（新固件已被回滚）。经 WiFi 升级时设备重启会断开连接，主机照常重连，新固件在新连接的 `hello` 里报告版本。

### 3.5 `line`

Agent 页用量卡上方的一条读数（§7.1「读数条」），目前来自「性能」插件：这台电脑的 CPU、GPU、内存、风扇、温度、磁盘。读数由主机上的插件生成并写好文字，设备只按通用的样式画，不知道每项是什么。网页的「设备预览」按同样的数据渲染（`GET /api/state` 里的 `line`）。

```json
{"t":"line","items":[
  {"id":"cpu","icon":"cpu","label":"CPU","text":"38","unit":"%","pct":38},
  {"id":"mem","icon":"memory","label":"内存","text":"88","unit":"%","pct":88,"level":"warn"},
  {"id":"temp","icon":"temp","label":"温度","text":"46","unit":"°C"}]}
```

设备收到后**整体替换**读数；空列表 `"items":[]` 表示不显示这一条（插件关着）。

发送时机：紧跟在每条 `snapshot` 后面。握手后、心跳时、固件升级没成功（设备没重启）后总是发送；状态变化时只在内容变了才发送。「性能」开着时读数每 2 秒变一次，`line` 也就每 2 秒发一次。设备收到同样 `id` 顺序的读数时只更新文字和进度条，不重排、不打断正在进行的轮换（§7.1）。

读数（最多 8 项，按顺序显示）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 读数 id：小写字母、数字、`-`、`_`，最长 16 字节。主机丢掉不合规的项 |
| `icon` | string | 可选。图标，见 §7.1；没有或不认识时不画 |
| `label` | string | 名称，最多 4 个字：`CPU`、`内存` |
| `text` | string | 读数，最多 8 个字，主机已写好：`38`、`3449`、`停转` |
| `unit` | string | 可选。紧跟在读数后面的单位，最多 4 个字：`%`、`rpm`、`°C` |
| `pct` | int | 可选。0–100，画成读数右边的进度条 |
| `sub` | string | 可选。没有 `pct` 时代替进度条的小字，最多 8 个字（「性能」的读数目前都不用） |
| `level` | string | 可选。`warn` 琥珀色、`crit` 红色，表示读数偏高；没有就是正常 |

字数按字符计，超出时主机截断并以「…」结尾；字段为假或为空时省略。

### 3.6 `beep`

让设备播放一段提示音。板子本身没有喇叭，要在排针上外接无源蜂鸣器（GPIO8，接法见 `firmware/README.md`「蜂鸣器提醒」）；没接时设备照常处理，只是不响。

```json
{"t":"beep","notes":[[2637,160],[0,40],[2093,320]],"vol":60}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `notes` | array | 依次播放的音符，每个是 `[频率 Hz, 时长 ms]`，频率 `0` 表示停顿。最多 320 个（多出的忽略；320 个最长的音也放得进一行 4096 字节）；频率 100–8000，超出范围按停顿处理；时长 10–1000 |
| `vol` | int | 可选。音量，百分比 1–100，超出范围取最近的有效值；缺省为 100。设备缩短 PWM 脉宽来调小音量，每低 1% 约小 0.5 dB（5% 约小 47.5 dB） |

设备收到后立刻播放，打断正在播放的那段。音色都在主机上定义（`host/internal/device/beep.go`：叮咚、嘀嘀、上扬、急促，以及 8-bit 风格的拾取、升级、过关、跳跃、警笛），用户也可以在设置里自己写音符（`device.beep_custom`），加新音色不用升级固件。

发送时机：有会话或子代理**开始**等用户处理（`approval` 需授权、`input` 等待输入）时，紧跟在那条 `snapshot`（和 `line`）后面发一次。同时开始等待的几个任务只响一次；一直等着不会重复响；设备重新插拔、重新握手后，不会为已经响过的任务再响；同一个会话被批准后又来一个授权请求，算新的一次。用户可以在设置里关掉（`device.beep`）。

用户在设置里打开「任务完成时响铃」（`device.beep_done`，默认关闭）后，会话从进行中、需授权或等待输入变成 `done`（按会话和子代理里最紧急的状态算，子代理也都结束才算）时，也用另选的提示音响一次；以 `error` 结束不算，go-dock 启动前就已完成的会话也不算。同一条 `snapshot` 里既有新的等待又有完成时，只响等待的那一种。静音（`device.mute`）时两种都不响。两种提示音都按设置里的音量（`device.volume`，5%–100%，默认 100%）发送，100% 时不带 `vol`。网页设置里点「在屏幕上试听」会立即发送一条，用表单里当前选的音量，不受这些设置影响。

### 3.7 `wifi`

让屏幕连上一个 WiFi（只支持 2.4 GHz），之后可以通过网络连接（§1.1）。**只在 USB 上有效**，设备忽略网络连接发来的 `wifi`，局域网里的人改不了屏幕连哪个网络。用户在网页上点「发给屏幕」时发一次。

```json
{"t":"wifi","ssid":"home","pass":"secret123","ip":"192.168.1.50","mask":"255.255.255.0","gw":"192.168.1.1"}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `ssid` | string | WiFi 名称，最多 32 字节；空字符串表示关掉 WiFi 并忘掉设置 |
| `pass` | string | 密码，8–63 个字符；没有密码的 WiFi 为空 |
| `ip` | string | **可选**。固定 IP；没有或为空时用 DHCP |
| `mask` | string | **可选**。子网掩码，有 `ip` 时默认 `255.255.255.0` |
| `gw` | string | **可选**。网关；电脑和屏幕不在同一网段时必须填，否则屏幕无法回复 |

设备把设置存起来（NVS），重启后自动连接，断线后按 1、2、4…30 秒退避重连。设置不对时（比如密码太短、IP 格式不对）回一条 `warn` 级的 `log`，设置不变。不管成功与否，处理完都回一条 `net`（§4.5）：接受了设置时它的 `state` 是 `connecting`（关掉 WiFi 时是 `off`），`ssid` 是新的名称，`fixed` 与有没有 `ip` 一致。主机靠这两点区分这次设置的结果和设备在读到设置之前发出的旧状态：先收到 `warn` 级 `log` 就是没接受；收到这样的 `net` 就是接受了，之后的 `net` 都是这次连接的进展，网页据此提示连上了还是连不上（`failed` 时的 `err`）。主机不记录密码，也不写进日志。正在扫描（§3.8）时设备拒绝新设置，回 `log`「正在扫描 WiFi，请几秒后再试」。

### 3.8 `wifi_scan`

让屏幕扫描附近的 WiFi，网页上列出来供用户点选。用屏幕自己的无线电扫描，所以列出的正是它能连的网络（2.4 GHz、在它的信号范围内）。**只在 USB 上有效**，条件同 §3.7。用户点「扫描」时发送。

```json
{"t":"wifi_scan"}
```

设备开始扫描，约 2–3 秒后回 `wifi_list`（§4.6）；不能开始时立即回带 `err` 的 `wifi_list`。没有设置 WiFi 时，设备只为这次扫描打开无线电，扫完再关；正在连接（或连不上、在等重试）时暂停连接，扫完继续；已连上时边连边扫。已经在扫描时不重复开始，结果照样回。主机 15 秒内收不到结果就报错。

## 4. 设备 → 主机

### 4.1 `hello`

上电后发送一次；每次收到主机 `hello` 时也回复一次。

```json
{"t":"hello","proto":1,"fw":"0.1.0","w":600,"h":450}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `proto` | int | 固件实现的协议主版本 |
| `fw` | string | 固件版本 |
| `w` / `h` | int | 屏幕分辨率 |

`proto` 与主机不一致时，主机在网页上报错，并**停止发送 `snapshot`**，但保持串口打开，仍可通过 §3.4 升级固件，升级后重新握手。

### 4.2 `ack`

可选。设备处理完一条 `snapshot` 后回复其 `seq`。主机只用它更新「最后响应时间」，不做重传。

```json
{"t":"ack","seq":128}
```

### 4.3 `log`

把固件日志转发到主机网页的「日志」页（带 `src=device` 标记）。

```json
{"t":"log","level":"info","msg":"battery 3.92V"}
```

`level` 取值为 `debug` / `info` / `warn` / `error`，无法识别时按 `info` 处理。

### 4.4 `ota`

设备对 §3.4 各条消息的回复。

```json
{"t":"ota","state":"confirm"}
{"t":"ota","state":"confirmed"}
{"t":"ota","state":"ready"}
{"t":"ota","state":"ack","off":2048}
{"t":"ota","state":"done"}
{"t":"ota","state":"error","msg":"写入失败（ESP_ERR_FLASH_OP_FAIL）"}
```

| `state` | 回复 | 说明 |
|---|---|---|
| `confirm` | `ota_begin`（WiFi） | 屏幕在问用户，还没擦除；接下来是 `confirmed` 或 `error` |
| `confirmed` | — | 用户点了「升级」，设备开始擦除，接下来是 `ready` |
| `ready` | `ota_begin` | 分区已擦除，可以发送数据 |
| `ack` | `ota_data` | `off` 为已写入的总字节数 |
| `done` | `ota_end` | 镜像有效，已设为启动分区，即将重启 |
| `error` | 任一条 | `msg` 说明原因；设备已放弃本次升级 |

### 4.5 `net`

屏幕的 WiFi 状态，**只在 USB 上发送**（含配对码）。设备回复 USB 上的 `hello` 后发一次，处理完 `wifi` 后发一次，之后 WiFi 状态变化时再发。

```json
{"t":"net","state":"connected","ssid":"home","ip":"192.168.1.50","port":47322,"code":"482916","fixed":true}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `state` | string | `off`（没设置 WiFi）、`connecting`（正在连接，或掉线后重连）、`connected`、`failed`（连不上，仍在重试） |
| `ssid` | string | **可选**。正在用的 WiFi 名称 |
| `ip` | string | **可选**。连上后的地址 |
| `port` | int | 监听的 TCP 端口，目前固定 47322 |
| `code` | string | 配对码 |
| `fixed` | bool | **可选**。为 `true` 表示用的是固定 IP |
| `err` | string | **可选**。`failed` 时的原因（中文），比如「密码不对」「找不到这个 WiFi（只支持 2.4 GHz）」 |

主机在网页上显示这些信息，用户可以一键把连接方式改成网络，地址和配对码自动填好。

### 4.6 `wifi_list`

扫描结果（§3.8），**只在 USB 上发送**。

```json
{"t":"wifi_list","aps":[{"ssid":"home","rssi":-48},{"ssid":"cafe","rssi":-80,"open":true}]}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `aps` | array | 找到的网络，按信号从强到弱，同名的只留最强的一个，隐藏网络不列；最多 20 个，一行放不下时从最弱的删起 |
| `aps[].ssid` | string | 名称 |
| `aps[].rssi` | int | 信号强度（dBm），越接近 0 越强 |
| `aps[].open` | bool | **可选**。为 `true` 表示没有密码 |
| `err` | string | **可选**。扫描失败的原因（中文），此时 `aps` 为空 |

### 4.7 `denied`

设备拒绝一条网络连接（§1.1），发完就断开（为了让主机先收到原因，断开前等 2 秒）。

```json
{"t":"denied","msg":"配对码不对，请对照屏幕上显示的配对码"}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `msg` | string | 原因（中文）：配对码不对、同一台电脑从新的连接连上了、连着屏幕的电脑太多了（超过 4 台）等 |

主机把原因显示在网页上，10 秒后再试。USB 连接不会被拒绝。

## 5. 时序

```
主机                                   设备
 │  连上屏幕（TCP 47322）                 │
 │──── hello ───────────────────────────▶│
 │──── snapshot(seq=1) ─────────────────▶│  渲染
 │◀─────────────────────────── hello ────│
 │──── snapshot(seq=2) ─────────────────▶│
 │◀──────────────────── ack(seq=2) ──────│  （可选）
 │      …… 状态变化（200 ms 防抖）或每 5 秒 ……
 │──── snapshot(seq=N) ─────────────────▶│
```

| 计时 | 值 | 说明 |
|---|---|---|
| 心跳 | 5 s | 主机至少每 5 秒发送一次 `snapshot` |
| 主机离线判定 | 15 s | 设备 15 秒内没有收到任何消息，应显示「主机离线」，保留最后的数据但置灰 |
| 握手重试 | 5 s | 主机在收到设备 `hello` 前每 5 秒重发 `hello` |
| 重新扫描 | 2 s | 串口断开或打不开时，主机每 2 秒重新查找设备 |
| 防抖 | 200 ms | 连续变化合并为一次发送 |
| 读数条 | 跟随 `snapshot` | `line` 紧跟在 `snapshot` 后发送，见 §3.5 |
| 提示音 | 跟随 `snapshot` | 有任务开始等用户处理（或打开了完成提醒时有任务完成）时，`beep` 跟在 `snapshot` 和 `line` 后面，见 §3.6 |
| 亮度 | 握手后、修改后 | `settings` 在收到设备 `hello` 后发送一次，用户改了设置再发，见 §3.3 |
| 网络连接配对 | 5 s | 网络连接 5 秒内没有带正确 `code` 的 `hello`，设备断开（§1.1） |
| 网络连接静默 | 20 s | 网络连接 20 秒没有任何消息，两端都断开 |
| 网络重连 | 5 s / 10 s | 主机连不上屏幕时每 5 秒重试；收到 `denied` 后等 10 秒 |

## 6. 版本规则

1. go-dock 和固件一起发布、一起升级：go-dock 在网页上把屏幕固件升到自己的版本（§3.4）。协议不为旧固件或旧主机保留兼容的写法。
2. 接收方忽略不认识的字段和不认识的 `t`。
3. 两端不能再互通的改动（删字段、改变字段含义或类型、改变帧格式）提升 `proto` 主版本。版本不一致时主机不再发数据，只保留升级。
4. 接收方遇到解析失败的行，丢弃该行并继续，不断开连接。
5. 固件升级用到的部分（§3.4、§4.4，以及 `hello` 的 `proto`、`fw`）在任何 `proto` 版本里都保持不变，并且不受版本不兼容影响：协议版本不一致的设备正是靠它升级。

### 7.2 时间计算

设备收到 `snapshot` 时记录 `base_now = now` 与 `base_ms = millis()`，之后：

```
当前时间 = base_now + (millis() - base_ms) / 1000
已持续   = 当前时间 - since
本轮时长 = turn_secs + (当前时间 - now)   （仅 running；需授权、等待输入时就是 turn_secs）
重置倒计时 = resets_at - 当前时间（≤0 时显示 `0m`）
```

这样两次 `snapshot` 之间界面的秒数也能平滑走动，不依赖板载 RTC。

### 7.3 其他

- **字库**：项目名、任务标题可能包含中文，需要内置 CJK 字库子集（例如 LVGL 字体转换器按常用 3500 字 + ASCII + 标点生成，16/20/24 px 各一套）。无法显示的字符用 `□` 代替，不要崩溃。
- **接收缓冲**：USB-Serial/JTAG 驱动的默认 RX 缓冲很小，请调到 ≥ 16 KB（`snapshot` 和 `line` 会连着到达，各最多 4 KB），并在单独任务里持续读取；写串口使用非阻塞或带超时的写入。
- **板子版本**：ESP32-S3-Touch-AMOLED-2.41 有 V1 / V2 两个硬件版本，**引脚定义不同，示例程序不通用**。V2 板丝印有「Rev2.0」或外壳贴「V2」标签。写固件前先确认手上的版本。
- **建议框架**：V2 用 ESP-IDF 6.1 + LVGL 9；V1 用 ESP-IDF ≥ 5.1.4 或 Arduino core ≥ 3.0.7 + LVGL 8.4。显示驱动 RM690B0（QSPI），触摸 FT6336（I2C）。
- **休眠**：深度/浅睡眠会让 USB 设备从主机上消失，主机会自动重连，但重连期间数据会中断。
